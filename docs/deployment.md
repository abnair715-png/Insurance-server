# Deploying the API to Render

The API is a long-lived Node process, not a serverless function. Render runs
`npm start` (`node dist/index.js`) and keeps it alive.

`render.yaml` in this folder is a Blueprint — you can either import it or mirror
its settings when creating the service by hand.

| Setting | Value |
| --- | --- |
| Service type | Web Service |
| Runtime | Node |
| Root Directory | *(repository root — leave blank)* |
| Build Command | `npm install --include=dev && npm run build` |
| Start Command | `npm start` |
| Health Check Path | `/api/health` |

> **`--include=dev` is not optional.** Render sets `NODE_ENV=production`, and npm
> reads `NODE_ENV` to decide what to install: under `production` it sets
> `omit=dev` and skips every devDependency. TypeScript is a devDependency, so
> without this the build fails with `sh: tsc: not found`.

> **Do not set `PORT` yourself.** Render injects it, and the app reads
> `process.env.PORT`. Hard-coding it makes the service unreachable.

## 1. MongoDB Atlas

1. Create a free **M0** cluster.
2. **Database Access** → add a user with *Read and write to any database*.
   Use the autogenerated password to avoid URL-encoding problems.
3. **Network Access** → add `0.0.0.0/0`.
   Render's free plan has no static outbound IP, so an allow-list is not
   possible. The database is protected by credentials and TLS, not by network
   position. A paid Render plan offers static outbound IPs if you need to narrow
   this.
4. Copy the connection string and insert the database name between the `/` and
   the `?`:

   ```
   mongodb+srv://<user>:<password>@<cluster>.mongodb.net/insurance_agent_platform?retryWrites=true&w=majority
   ```

## 2. Stripe (test mode)

**Developers → API keys** → copy the **Secret key** (`sk_test_…`). Leave
`STRIPE_WEBHOOK_SECRET` empty for now; it needs the deployed URL (step 5).

## 3. Resend (optional)

Create an API key (`re_…`). For the sender:

- **With your own domain** — verify it, then use
  `EMAIL_FROM="Sentinel General Insurance <noreply@your-domain.com>"`.
- **Without one** — use `onboarding@resend.dev`, which only delivers to the
  address that owns the Resend account. Set `SEED_CUSTOMER_EMAIL_OVERRIDE` to
  that address so the seeded customers are reachable.

Leave `RESEND_API_KEY` empty and emails are written to the Render logs instead
of being sent. Everything else works unchanged.

## 4. Create the Render service

**New → Web Service → connect this repository.** Leave Root Directory blank —
the repository root is the service root.

Apply the build/start/health settings from the table above, then add the
environment variables:

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `MONGODB_URI` | from step 1 |
| `JWT_SECRET` | `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"` |
| `JWT_EXPIRES_IN` | `12h` |
| `DOCUMENT_LINK_SECRET` | a **different** value, generated the same way |
| `DOCUMENT_LINK_TTL_HOURS` | `168` |
| `CLIENT_URL` | `http://localhost:5173` — placeholder, corrected in step 6 |
| `API_PUBLIC_URL` | leave empty until this service has a URL |
| `CORS_ADDITIONAL_ORIGINS` | empty, or a comma-separated list — see below |
| `STRIPE_SECRET_KEY` | from step 2 |
| `STRIPE_WEBHOOK_SECRET` | empty for now — step 5 |
| `STRIPE_CURRENCY` | `inr` |
| `RESEND_API_KEY` | from step 3, or empty |
| `EMAIL_FROM` | from step 3 |
| `COMPANY_NAME` | `Sentinel General Insurance` |
| `COMPANY_SUPPORT_EMAIL` | your support address |
| `COMPANY_SUPPORT_PHONE` | your support number |

Deploy. Note the URL — `https://<service>.onrender.com`, call it `<API_URL>` —
then set `API_PUBLIC_URL=<API_URL>` and redeploy.

Confirm it is alive:

```bash
curl <API_URL>/api/health
# {"success":true,"data":{"status":"ok","environment":"production",...}}
```

## 5. Stripe webhook

**Developers → Webhooks → Add endpoint** (test mode):

- URL: `<API_URL>/api/webhooks/stripe`
- Events: `checkout.session.completed`, `checkout.session.expired`,
  `checkout.session.async_payment_succeeded`,
  `checkout.session.async_payment_failed`, `payment_intent.payment_failed`

Copy the **Signing secret** (`whsec_…`) into `STRIPE_WEBHOOK_SECRET` and
redeploy. Until it is set the endpoint returns `503` and payments never settle.

### Allowing more than one client origin

`CLIENT_URL` accepts a **comma-separated list**:

```
CLIENT_URL=https://firsturl.com,https://secondurl.com
```

- The **first** entry is canonical — it is where Stripe returns the customer
  after checkout, and the fallback for `API_PUBLIC_URL`.
- **Every** entry is added to the CORS allow-list.

`CORS_ADDITIONAL_ORIGINS` takes the same format, for origins that should be
allowed but must never become the redirect target — a Vercel preview build, an
internal tool:

```
CORS_ADDITIONAL_ORIGINS=https://firsturl.com,https://secondurl.com
```

Each entry must be a **full origin including the scheme**. `firsturl.com` is
ignored with a warning at boot, because a browser's `Origin` header never looks
like that. A trailing slash or a capitalised host is fine — both sides are
normalised, so `https://FirstURL.com/` matches `https://firsturl.com`.

A rejected origin is **logged with the exact value and the current allow-list**,
and denied by omitting the CORS headers rather than by throwing — so the browser
reports a clean CORS error instead of a 500, and non-browser callers such as the
Stripe webhook are unaffected.

## 6. Point the API at the client

Once the client is deployed (see its
[deployment guide](https://github.com/abnair715-png/Insurance-Agent-Platform-client/blob/main/docs/deployment.md)), set
`CLIENT_URL` to the client's origin and redeploy.

**Until you do this the browser is blocked by CORS**: the login page renders,
and every request fails with a network error in the console.

## 7. Seed the production database

Required, not optional — `autoIndex` is disabled in production, so this is what
creates the unique indexes the idempotency guarantees depend on.

Run it from your own machine against the Atlas URI:

```bash
# create .env with the keys from the README's Environment variables table,
# filling in MONGODB_URI and the SEED_AGENT_* values
npm run check-env -- --seed
npm run seed
rm .env
```

Or from Render's **Shell** tab (paid plans only): `npm run seed`.

## The free plan spins down

After ~15 minutes of inactivity Render's free plan stops the service, and the
next request pays a cold start of roughly 50 seconds.

What that means in practice:

| Situation | Effect |
| --- | --- |
| Reviewer opens the dashboard after a quiet period | First request hangs for ~50s, then everything is normal |
| Stripe delivers a webhook while spun down | The delivery times out, **then Stripe retries with backoff** and it succeeds. The handler is idempotent, so a retry is harmless — this is exactly the case `docs/payment-idempotency.md` covers |
| A customer opens a PDF share link | Same cold start, then the PDF renders |

Ways to avoid it during a demo:

- Open `<API_URL>/api/health` a minute before you present.
- Point a free uptime pinger (UptimeRobot, cron-job.org) at `/api/health` every
  10 minutes.
- Upgrade to Render's Starter plan, which does not spin down.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Build fails: `sh: tsc: not found` | `NODE_ENV=production` makes npm skip devDependencies | Build command must be `npm install --include=dev && npm run build` |
| Deploy succeeds, service marked unhealthy | Health Check Path wrong, or the app bound to the wrong port | Path is `/api/health`; never set `PORT` yourself |
| First request after a pause takes ~50s | Free-plan spin-down | See above |
| Dashboard loads but every request fails with a CORS error | `CLIENT_URL` does not exactly match the client's origin | Set it (with `https://`, no trailing slash) and redeploy |
| Webhook returns `503` | `STRIPE_WEBHOOK_SECRET` not set | Step 5 |
| Webhook returns `400` | Signing secret belongs to a different endpoint | Re-copy the secret for *this* endpoint |
| Payment succeeds in Stripe but no policy | Webhook never delivered, or the service was down long enough to exhaust retries | Check Stripe → Webhooks → delivery attempts; resend the event |
| WhatsApp PDF links 404 | `API_PUBLIC_URL` unset, so links were built from `CLIENT_URL` | Set it to `<API_URL>`, redeploy, regenerate the document |
| `MongoServerSelectionError` | Atlas Network Access, or an unencoded password | Allow `0.0.0.0/0`; URL-encode `@ : / # ? %` |
| Duplicate-key errors on first write | Seed not run, so indexes are missing | Step 7 |
| Login works then immediately 401s | `NODE_ENV` not `production`, so `Secure` is unset on the cookie | Set `NODE_ENV=production` |

## Local development

```bash
npm install
# create .env — see the README's Environment variables table
npm run seed
npm run dev             # http://localhost:4000
```

`CLIENT_URL` should be `http://localhost:5173` and `API_PUBLIC_URL` empty — the
Vite dev proxy makes the two same-origin locally.

### Testing Stripe locally

```bash
stripe login
stripe listen --forward-to localhost:4000/api/webhooks/stripe
# copy the printed whsec_... into STRIPE_WEBHOOK_SECRET, restart the server
```

To prove idempotency by hand, replay a delivered event:

```bash
stripe events resend evt_xxx
```

The second delivery returns `200 {"processed": false, "reason":
"duplicate_event_already_processed"}`, and no second policy or email appears.
